Where the project's instructions differ from the template's, the project's win. Claude Code reads this file through `CLAUDE.md` and imports each `@` file. This file belongs to the project: template updates never change it. Keep it under 200 lines; put anything longer in a listed file.

## Commands

Run from the repository root in PowerShell 7.

- Build: `dotnet build`
- Test: `dotnet test`
- Coverage: `./build/Test-Coverage.ps1` runs the tests with coverage, lists every line no test runs, and fails below 98% line or branch coverage; CI runs it after the Definition of Done
- Gate: `./build/gate.ps1` (the full gate CI runs) or `./build/gate.ps1 -Fast` (Debug, no pack): the CSharpier check, then the Definition of Done, `./build/dod.ps1`, which ends with `Definition of Done: PASSED`. Record a public API change with `./build/Update-PublicApi.ps1`
- Format: `dotnet tool restore` once, then `dotnet csharpier format .`
- Site: with [NCodeGroup/docs](https://github.com/NCodeGroup/docs) cloned beside this repository and set up as its README says, `npm --prefix ../docs run dev '--' .` serves the documentation site from `docs/site/`, and `npm --prefix ../docs run site '--' build . --out <folder>` builds it into a folder outside this repository; neither writes here. The `--` is quoted so PowerShell passes it to npm

## Landing

How `/ship-plan` lands a reviewed plan. `integrate`: `pull-request` pushes the plan's branch and opens a pull request; `direct` pushes to the default branch. `release`: `none`; `tag` tags the plan's `Release:` version, or the next free one when another plan landed it first; `tag+release` also publishes a release from that version's section of `changelog`. On GitHub, `.github/workflows/tag-release.yml` tags and publishes it as the pull request merges, from the `Release:` line `/ship-plan` writes in its description or the changelog's newest section, and for a .NET library starts `.github/workflows/publish.yml`; `/ship-plan` run after the merge does only what that workflow didn't. `changelog`: the file every plan's last step writes, in the Keep a Changelog format, `CHANGELOG.md` by default. `pre-release`: `untracked` keeps the project pre-release until a version tag of 1.0.0 or later: nothing it released or stored has a reader that must keep working, so every text describes the product as it is, the changelog's `## [Unreleased]` is a catalog of what the product does that each plan edits in place, and a breaking change needs no deprecation or migration path, as ADR-0015 in `docs/decisions/project-template/` says; `tracked`, the default when the line is missing, tracks every change from the first release, for a project whose releases or stored data already have readers. `draft`: `no`, the default when the line is missing, which a template update never changes, so a project lands as it did; `yes` opens every pull request as a draft, as `/ship-plan draft` does, and a new project that runs NCode Review starts with it, since its approval lets a ready pull request merge, so marking it ready is the person's review (ADR-0022 in `docs/decisions/project-template/`); and `/run-issues` opens its pull requests as drafts either way. `follow-ups`: `issues` files a plan's follow-ups as issues in this repository; `<owner/repo>` files them in that repository; `none` files none, and `/ship-plan` lists them for you to record. `follow-up-label`: the label those issues get, `follow-up` by default; write a name with spaces as it is, such as `tech debt`. `gate`: `none`; a command, such as `./build/dod.ps1 -Fast`, that `/ship-plan`, `/run-issues`, `/address-feedback` and `/run-feedback` run from the repository root before each push, stopping when it exits non-zero or changes a file. `protect`: `none`; `hook` makes `.githooks/pre-push` refuse any push to the default branch, for a host that can't require pull requests, such as a private repository on GitHub Free. `pr-format`: `none`; `<file>#<heading>`, such as `AGENTS.md#Pull requests`, names the section that sets the title and description of the pull requests `/ship-plan` opens, which still end with their `Closes` lines. `review-bots`: the review bots, by login and separated by commas, whose findings `/run-issues`, `/address-feedback` and `/run-feedback` may fix, `ncode-review` by default, or `none`; `/run-issues` and `/run-feedback` judge every one of NCode Review's findings, whatever its severity, and fix each that holds, and a bot's finding alone never changes CI, the template, agent configuration, the build or the dependencies: `/address-feedback` and `/run-feedback` change them only when you approve it in their start question. `max-review-rounds`: `3`; after that many rounds of review feedback on a pull request, `/run-issues` and `/run-feedback` comment no further `/review`, so NCode Review isn't asked to review again, and still fix and answer every finding; they recommend the merge once every finding is fixed, declined or answered and the review of the last push they asked for is in. `prelude`: `none`; one PowerShell command that sets up the shell the workflow's commands run in, such as `./build/env.ps1`, a script in the repository, or `nvs use 26`, to put a tool installed through a version manager on `PATH`. `/ship-plan`, `/run-issues`, `/address-feedback` and `/run-feedback` run it before the gate, and executors and coordinators before each Done-when command, dot-sourced in the same PowerShell; a plan names it under Context for the executor, so no step repeats it. When it fails, they stop and show its error. Write it on one line, without a leading `. ` or `& ` operator, a `#` comment, or `;`, `|`, `&`, `&&` or `||`; `.template/Get-PlanState.ps1` prints any other value as `prelude=invalid`, and `/ship-plan` stops on it. `/run-issues` runs only when the host requires pull requests into the default branch, or `protect` is `hook` and the hooks are enabled.

- integrate: pull-request
- release: tag+release
- changelog: CHANGELOG.md
- pre-release: tracked
- draft: yes
- follow-ups: issues
- follow-up-label: follow-up
- gate: ./build/gate.ps1 -Fast
- protect: none
- pr-format: none
- review-bots: ncode-review
- max-review-rounds: 3
- prelude: none

## Conventions

- A public API change is recorded with `./build/Update-PublicApi.ps1`; a published GitHub release starts `.github/workflows/publish.yml`, which pushes the packages to nuget.org through trusted publishing, with no stored API key (ADR-0135 in `docs/decisions/project-template/`). The Landing section sets `release: tag+release`, so `.github/workflows/tag-release.yml` tags and publishes each release as its pull request merges and starts `publish.yml` (ADR-0016 and ADR-0137).
- This repository accepts the template's ADR-0006 exception for `.github/workflows/code-review-auto-merge.yml`: a Dependabot pull request whose one change is the NCode Review pin may be auto-merged.
- Releases of NCodeGroup/docs, the documentation site's toolchain, are adopted the day they are published while the NCode brand, the toolchain and the first sites built with them are built out (ADR-1024 in `docs/decisions/`), which overrides project-template ADR-0009's three-day cooldown for that one dependency: `.github/dependabot.yml` excludes it from the cooldown, until NCodeGroup/docs 1.0.0 or the maintainers end the build-out. Every other dependency, NCode Review included, waits three days.
- Versions come from `version.json` through Nerdbank.GitVersioning (ADR-1000 in `docs/decisions/`), which overrides project-template ADR-0136's version from the release tag: `version` is the version the next release ships. A change that adds public API raises it to the next minor version, a breaking change to the next major, and a plan with a `Release:` line sets it to that version, because `publish.yml` publishes nothing when the tag and `version.json` disagree.
- Every pack is validated against the package `PackageValidationBaselineVersion` names in `src/NCode.Buffers/NCode.Buffers.csproj` (ADR-1001), and `.github/workflows/raise-baseline.yml`, which `publish.yml` calls after each publish, opens the draft pull request that raises it (ADR-0150 and ADR-0151 in `docs/decisions/project-template/`); `build/Update-Baseline.ps1 -Version <version>` does it by hand. `docs/api-compatibility.md` is the procedure for changing the public API.
- CSharpier formats the code (ADR-1002): run `dotnet csharpier format .` before committing. Every C# file starts with the two lines `// Copyright © NCode Group` and `// SPDX-License-Identifier: Apache-2.0`.
- The C# samples in `README.md` and `src/NCode.Buffers/README.md` are copied by MarkdownSnippets from `tests/NCode.Buffers.Tests/ReadmeSamplesTests.cs` and `tests/NCode.Buffers.Tests/ReadmeSamples/Signatures.cs` (ADR-1005): change a sample in its test, between `// begin-snippet: <name>` and `// end-snippet`, then run `dotnet mdsnippets`; never edit a README's `<!-- snippet: -->` block, which `./build/gate.ps1` checks against the tests. A `#region` name in a test needs a space, or MarkdownSnippets reads it as a snippet.
- Every `<code>` example in the XML documentation of `src/NCode.Buffers` compiles as written: `./build/Test-XmlDocExamples.ps1`, which `./build/gate.ps1` runs, builds each as a method body against the library. An example may call `ProcessData(ReadOnlySpan<byte>)` and read `memoryOwner`, an `IMemoryOwner<byte>`, which the script declares; anything else it uses, it declares itself.
- The documentation site's content is in `docs/site/`, and the shared toolchain in NCodeGroup/docs builds it (ADR-1009): this repository gets no `package.json`, no lockfile and no Node.js code. A page is an `.mdx` file, never `.md`, listed in the `sidebar` of `docs/site/site.config.json`, with links to other pages written from the site's root with a trailing slash; the toolchain's `CONTRACT.md` is the reference. `.github/workflows/docs.yml` builds the site on every pull request, with the toolchain pinned by commit, and publishes nothing: [#56](https://github.com/NCodeGroup/Buffers/issues/56) tracks publishing it, so no document links to it.
- A page never holds C# that must compile: it includes a sample with an empty `cs snippet=<Key>` code block, and the site's build fills it (ADR-1010). Site samples are tests in `tests/NCode.Buffers.Site.Tests`, which cannot see the library's internal members: one class per page, named for the page's file in a folder named for the page's folder (`docs/site/guides/verify-a-mac.mdx` has `Guides/VerifyAMacSamples.cs`), besides the `SecretAssert` helper and its tests, and one fact per sample, named `<Key>Sample_Runs`, with the sample between `// begin-snippet: <Key>` and `// end-snippet`, each alone on its line. A sample key is PascalCase letters and digits, defined once in the repository whatever its letter case; a site sample's key starts with `Site` and no README sample's does, and `./build/gate.ps1` checks the markers and all three rules. A page may also include a README sample by its key.
- A page never holds a copy of a repository file either: it shows the file, whole or from the line that holds one text to the line that holds another, with an empty `file=<path>` code block, such as `xml file=Directory.Build.props from="<ItemGroup" to="</ItemGroup>"`, which the site's build fills and links to those lines at the commit it was built from (NCodeGroup/docs `CONTRACT.md` section 4, NCodeGroup/docs ADR-1010). The site's components style themselves with the brand's public tokens: the `--nc-` colour roles, spacing, radii, borders, elevation, motion, focus, controls and font families, the type roles' `-stretch` and `-tracking` parts, and Starlight's `--sl-text-*` sizes, never a step of a colour ramp or of the type scale; the site's build fails a component that reads one, or a `--nc-` token the brand does not define (NCodeGroup/docs ADR-1012).
- A guide has the headings the `requiredHeadings` rules of `docs/site/site.config.json` list, in order, and the site's build fails one without them (NCodeGroup/docs ADR-1011); a guide that is a numbered procedure, ending with `## Check your work`, is added to the first rule's `except` and the second rule's `pages`. `build/Update-ReviewChecklist.ps1` gathers the Checklist sections of the guides a rule that lists `## Checklist` covers into the review checklist page's data, and `./build/gate.ps1` fails when the data is stale or a covered guide has no Checklist.
- Shipping code takes buffers from `BufferFactory` and text encodings from `SecureEncoding`: `BannedSymbols.Encoding.txt` and `BannedSymbols.Buffers.txt` ban the rest outside test projects (ADR-1003).
- Documentation names no .NET version or target framework moniker: `src/NCode.Buffers/NCode.Buffers.csproj` is the only source of truth for the target frameworks. A README shows them through the Shields.io dynamic XML badge that reads `TargetFramework` or `TargetFrameworks` from that file, and links to nuget.org's Frameworks tab; `CHANGELOG.md` records when a framework is added or dropped.
- A README table has at most three short columns, with facts every row shares written in the sentence above it, so it fits GitHub's README column, 555 pixels wide in a 1012-pixel window, without scrolling sideways; a README code line stays under 100 characters, the width of the column in a 1280-pixel window.
- The OpenSSF Scorecard badge is only in the root `README.md`: nuget.org doesn't render images from `api.scorecard.dev`, so the package README, `src/NCode.Buffers/README.md`, leaves it out. `.github/workflows/scorecard.yml` publishes the score, and Scorecard rejects it once that workflow gains workflow-level `env`, `defaults` or write permissions, or its job gains `env`, `defaults`, a container, services or a step outside Scorecard's approved actions.
