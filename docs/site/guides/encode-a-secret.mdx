This is your situation when your code turns a secret between text and bytes: a key that arrives as Base64 or hex, a
password you need as bytes, or a random key you need to generate and write out as text. The example decodes a key,
encodes a password and makes a nonce.

## The usual code

It converts with the standard methods. Each one returns a new array that nothing zeroes, and that stays on the heap
until the garbage collector reclaims it.

<Pinned tone="usual">
```cs snippet=SiteEncodeSecretUsual title="Secrets.cs" "Convert.FromBase64String(" "RandomNumberGenerator.GetBytes("
```
</Pinned>

**Leaves behind**

<PinNotes tone="usual">

1. `key` is an array of the decoded key. It holds the secret until the garbage collector reuses the memory, and your
   code has no call that clears it for you.
2. `nonce` is an array of random bytes, and it is left behind in the same way. The password's array has the same
   problem: `Encoding.UTF8.GetBytes` returns one, and it is not zeroed either.

</PinNotes>

## With NCode.Buffers

`BinaryTextEncoding.RentDecoded` decodes the text into a rented buffer, and returns the owner of that buffer. The
format names the text: `Base64`, `Base64Url`, `Base64UrlStrict`, `HexUpper` or `HexLower`. With `isSensitive: true`,
disposing the owner zeroes the bytes before the buffer goes back to the pool.

</Pinned>

**What changed**

[What this does not fix](#what-this-does-not-fix).

### A password as bytes

`SecureEncoding.UTF8.RentBytes` encodes text into a rented buffer. It counts the bytes first, and then rents exactly
that many. Text that cannot be encoded, such as a high surrogate with no low surrogate after it, throws

array that nothing zeroes. <Proof test="BufferFactoryTests.RentRandom_WithSpan_ReturnsRandomBytesOfTheRequestedLength" />

### Strict Base64url for JOSE

A JWS, a JWE and a JWK hold Base64url with no padding, and RFC 7515 allows one spelling of each value. `Base64Url`
also accepts `=` padding and whitespace when it decodes. `Base64UrlStrict` accepts only the URL-safe alphabet, with no
padding, no whitespace and no unused bit set in the last character, and throws `FormatException` for anything else.
Both formats encode the same text.

### Invalid text

Text that is not in the format throws `FormatException`. The rental is returned before the exception reaches your
code, and it is zeroed first when it is sensitive. <Proof test="BinaryTextEncodingTests.RentDecoded_InvalidText_ThrowsFormatException" />

## Pitfalls

[Ways to get it wrong](/reference/pitfalls/) has more, each with its evidence.

<Pitfalls>

- **Keeping the owner and the span apart.**
  - *You write* a method that returns the `Span<byte>` and lets the owner go out of scope.
  - *What happens:* the owner is never disposed, so the buffer is never zeroed.
  - *Write instead:* keep the owner in the scope that uses the span, and dispose it there.
- **Forgetting `isSensitive: true`.**
  - *You write* the call without it.
  - *What happens:* the buffer goes back to the pool with the secret still in it.
  - *Write instead:* pass `isSensitive: true` for every secret.
- **Copying the span.**
  - *You write* `key.ToArray()` or `new string(text)`.
  - *What happens:* the copy is an array or a string that nothing zeroes. <Proof sample="SiteEncodeSecretUsual" />
  - *Write instead:* pass the span on, and do not make a copy.
- **Assuming invalid text decodes anyway.**
  - *You write* a call with no `catch`.
  - *What happens:* text that is not in the format throws `FormatException`.
    <Proof sample="SiteEncodeSecretRejectInvalid" />
  - *Write instead:* catch it where the text enters, and turn it into a rejection.

</Pitfalls>

## What this does not fix

:::caution[Outside text and bytes conversion]
- **The text itself.** A `string` from a header or a configuration file cannot be zeroed, so the key is still in
  memory as that string. [What it protects, and what it does not](/start/limits/).
- **A copy you make.** `ToArray()`, `new string(…)` and `ToString()` each make a copy that nothing zeroes.
- **What a library does inside.** A JWT or JWK library that takes the text or the bytes decides for itself what it
  copies.
:::

## Checklist

- Every key and password is made with `RentDecoded`, `RentBytes`, `RentChars`, `RentEncoded` or `RentRandom`,
  and not with `Convert.FromBase64String`, `Encoding.UTF8.GetBytes` or `RandomNumberGenerator.GetBytes`.
- Every call that handles a secret passes `isSensitive: true`; a nonce, which is not secret, may pass `false`.
- The owner is held in the scope that uses its span, and disposed with `using`.
- `FormatException` and `EncoderFallbackException` are caught where the input enters.
- JOSE values, such as a JWK's key or a JWS signature, are decoded with `Base64UrlStrict`, not `Base64Url`.
- Nothing copies the span with `ToArray()` or `new string(…)`.
