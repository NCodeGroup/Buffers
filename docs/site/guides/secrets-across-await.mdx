This is your situation when the code that uses a key is async, or the key lives as long as the application, and the
span-based types will not compile there. The examples read a key from a stream and verify a MAC with it, and hold a
signing key for the life of the application.

You'll use `BufferFactory.Rent` with `out Memory<byte>` · `IMemoryOwner<byte>` · `GetSecureLifetime()` ·
`HMACSHA256`

## The usual code

The quick start's shape, in an async method, does not compile:

```cs title="Does not compile: CS4007" {5}
static async Task<bool> VerifyAsync(Stream keySource, byte[] message, byte[] mac)
{
    using var owner = BufferFactory.Rent(32, isSensitive: true, out Span<byte> key);
    await keySource.ReadExactlyAsync(owner.Memory[..32]);
    byte[] expected = HMACSHA256.HashData(key, message);
    return CryptographicOperations.FixedTimeEquals(expected, mac);
}
```

The compiler stops at `key` on the marked line: "Instance of type 'System.Span\<byte\>' cannot be preserved across
'await' or 'yield' boundary." A span lives only on the stack. <Proof external="SpanStackOnlyDocs" /> So the usual code
falls back to an array, and a long-lived key to an array in a field.

**Leaves behind**

<PinNotes tone="usual">

1. The key in an ordinary array for as long as the method runs, its awaits included. A compaction in that time can
   copy the array and leave the old cells behind. <LeakCard leak="L1" />
2. The expected MAC in a second array. Nothing clears either one when the method ends. <LeakCard leak="L2" />
3. A key in a field, for as long as the object lives: for a signer the application holds, until the process ends.
   Every compaction until then can leave one more copy. <LeakCard leak="L1" />

</PinNotes>

## With NCode.Buffers

The same two jobs. An async method takes the `Memory<byte>` overload of `Rent`, and does its span work in a
synchronous helper. A long-lived key is held by a class of its own, which you dispose.

**What changed**

<PinNotes tone="fix">

1. The key is in a buffer from `Rent`. The `Memory<byte>` overload uses the same pool and the same owner as the span
   overload, and its view can cross an `await`. The buffer is pinned, so no compaction copies it, however long the
   method waits. <Proof source="BufferFactory.RentMemory" /> <Proof claim="R3" />
2. The expected MAC is on the stack of a synchronous helper, and its lifetime overwrites it with zeros when the
   helper returns. <Proof claim="R1" />
3. The long-lived key is held through its `IMemoryOwner<byte>`, by a class that is disposable itself, as Microsoft's
   guidance for a type that holds an owner says. Its `Dispose` overwrites the key with zeros.
   <Proof external="MemoryOwnerHolderDocs" /> <Proof claim="R1" />

</PinNotes>

## Where each type can live

When the key is rented, and when it is zeroed, in each of the three places:

<SecretsAcrossAwaitTimeline />

What you hold decides where it can go: the left column stays on the stack, the right can cross an `await` and live in
a field.

| Stack only | Can be stored |
| --- | --- |
| `Span<T>` from `Rent`, and `stackalloc` memory | `IMemoryOwner<T>` from `Rent`, and its `Memory<T>` |
| `SecureArrayLifetime<T>` from `CreatePinnedArray` | `SecureMemoryPool<T>` |
| `SecureSpanLifetime<T>` from `GetSecureLifetime()` | `Sequence<T>` from `CreatePooledBufferWriter` |
| `RefSpanLease<T>` from `GetSpanLease` | The owner `ConsumeAsContiguousSpan` returns |
| The span `ConsumeAsContiguousSpan` returns | `FixedMemoryBufferWriter<T>` |
| `FixedSpanBufferWriter<T>` | `ArrayBufferWriter<T>` from `CreateArrayBufferWriter` |
| | `MemorySegment<T>`, `EmptyMemory<T>`, `StringSegments` |

## Pitfalls

Each is also in [Ways to get it wrong](/reference/pitfalls/), with its evidence.

- **`using var` at the top of a long async method.** *You write* `using var keyOwner = …` and then await more work.
  *What happens:* the key stays in memory until the method returns, every await included.
  <Proof external="UsingDeclarationDocs" /> *Write instead:* a `using` block, or a helper, that ends where the key's
  use ends.
- **A view kept after `Dispose`.** *You write* a field or a captured variable that keeps the `Memory<byte>` after its
  owner is disposed. *What happens:* nothing throws, and the pool may have rented the memory to another caller by
  then. *Write instead:* keep the owner, and take the view from it when you use it, as `SigningKey` does.
  [A view kept after Dispose](/reference/pitfalls/#a-view-kept-after-dispose)
- **A key for the life of the application.** *You write* a key held until the process ends. *What happens:* pinning
  keeps the collector from copying it; it is still readable for as long as it lives. <Proof claim="R3" /> *Write
  instead:* hold it no longer than it is needed, and dispose its holder when it is replaced.
  [A key kept for the life of the process](/reference/pitfalls/#a-key-kept-for-the-life-of-the-process)
- **Disposing a key another thread is using.** *You write* `signingKey.Dispose()` at shutdown or rotation while a
  request is still signing. *What happens:* `Dispose` takes no lock and does not wait for readers, so the other call
  can read zeros halfway through. <Proof source="SecureMemory.Dispose" /> *Write instead:* stop handing the key out
  first, and dispose it once no call can reach it.

## What this does not fix

:::caution[Outside this guide]
- **How long the key has to exist.** A key the application needs all day is in memory all day.
- **Who else holds a reference to it,** such as an algorithm object that copied it.
- **Readers outside your code.** A debugger, a crash dump or the page file can read a key while it is in memory:
  [what it protects, and what it does not](/start/limits/).
:::

## Checklist

- [ ] Async code takes the `Memory<byte>` overload of `Rent`.
- [ ] A long-lived key is held through an `IMemoryOwner<byte>` in a disposable class, never in a `byte[]` field.
- [ ] The holder is disposed at shutdown or rotation, once nothing still uses it.
- [ ] No span or `Memory<T>` of the buffer outlives its owner.
- [ ] Span work happens in synchronous helpers, or in blocks that end before the next `await`.
