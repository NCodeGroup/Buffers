This is your situation when the code that uses a key is async, or the key lives as long as the application, where
the span-based types do not compile. The examples verify a MAC with a key read from a stream, and hold a signing key
for the life of the application.

You'll use `BufferFactory.Rent` with `out Memory<byte>` · `IMemoryOwner<byte>` · `GetSecureLifetime()` ·
`HMACSHA256`

## The usual code

The quick start's shape, in an async method, does not compile:

```cs title="Does not compile: CS4007" {5}
static async Task<bool> VerifyAsync(Stream source, byte[] message, byte[] mac)
{
    using var owner = BufferFactory.Rent(32, isSensitive: true, out Span<byte> key);
    await source.ReadExactlyAsync(owner.Memory[..32]);
    byte[] expected = HMACSHA256.HashData(key, message);
    return CryptographicOperations.FixedTimeEquals(expected, mac);
}
```

On the marked line the compiler stops at `key`: "Instance of type 'System.Span\<byte\>' cannot be preserved across
'await' or 'yield' boundary." A span lives only on the stack. <Proof external="SpanStackOnlyDocs" /> So the usual code
falls back to an array, in a field for a long-lived key.

**Leaves behind**

<PinNotes tone="usual">

1. The key in an ordinary array for as long as the method runs, its awaits included, where a compaction can copy
   it. <LeakCard leak="L1" />
2. The expected MAC in a second array. Nothing clears either one when the method ends. <LeakCard leak="L2" />
3. A key in a field, for as long as the object lives: for the application's signer, until the process ends.

## Where each type can live

When the key is rented and zeroed, in each of the three places:

<SecretsAcrossAwaitTimeline />

The left column stays on the stack; the right can cross an `await` and live in a field.

| Stack only | Can be stored |
| --- | --- |
| `Span<T>` from `Rent`, and `stackalloc` memory | `IMemoryOwner<T>` from `Rent`, and its `Memory<T>` |
| `SecureArrayLifetime<T>` from `CreatePinnedArray` | `SecureMemoryPool<T>` |
| `SecureSpanLifetime<T>` from `GetSecureLifetime()` | `Sequence<T>` from `CreatePooledBufferWriter` |
| `RefSpanLease<T>` from `GetSpanLease` | The owner `ConsumeAsContiguousSpan` returns |
| The span `ConsumeAsContiguousSpan` returns | `FixedMemoryBufferWriter<T>` |
| `FixedSpanBufferWriter<T>` | `ArrayBufferWriter<T>` from `CreateArrayBufferWriter` |
| | `MemorySegment<T>`, `EmptyMemory<T>`, `StringSegments` |

The library's types on the left are declared `ref struct`. <Proof source="SecureArrayLifetime.Declaration" /> <Proof source="SecureSpanLifetime.Declaration" /> <Proof source="RefSpanLease.Declaration" />
<Proof source="FixedSpanBufferWriter.Declaration" /> The compiler refuses one that is still in use after an `await`
(CS4007), as a field of a class (CS8345) and inside a lambda (CS8175), each checked by hand with the compiler.

## Pitfalls

[Ways to get it wrong](/reference/pitfalls/) has more, each with its evidence.

- **`using var` at the top of a long async method.** *You write* `using var keyOwner = …`, then await more work.
  *What happens:* the key stays until the method returns. <Proof external="UsingDeclarationDocs" /> *Write instead:*
  a `using` block, or a helper, that ends with the key's use.
- **A view kept after `Dispose`.** *You write* a field that keeps the `Memory<byte>` after its owner is disposed.
  *What happens:* nothing throws, and the pool may have rented that memory to another caller. *Write instead:* keep
  the owner, and take the view when you use it, as `SigningKey` does.
  [A view kept after Dispose](/reference/pitfalls/#a-view-kept-after-dispose)
- **Disposing a key another thread is using.** *You write* `signingKey.Dispose()` while a request is still signing.
  *What happens:* `Dispose` takes no lock, so that call can read zeros halfway through.
  <Proof source="SecureMemory.Dispose" /> *Write instead:* stop handing the key out, then dispose it.

## What this does not fix

:::caution[Outside this guide]
- **How long the key exists.** A key needed all day is in memory all day, pinned but readable:
  [A key kept for the life of the process](/reference/pitfalls/#a-key-kept-for-the-life-of-the-process).
- **Who else holds a reference to it,** such as an algorithm object that copied it.
- **Readers outside your code,** such as a debugger, a crash dump or the page file:
  [what it protects, and what it does not](/start/limits/).
:::

## Checklist

- Async code rents with `out Memory<byte>`.
- A long-lived key is in an `IMemoryOwner<byte>` held by a disposable class, never in a `byte[]` field.
- The holder is disposed at shutdown or rotation, once nothing uses it.
- No view of the buffer outlives its owner.
- Span work is in synchronous helpers, or in blocks that end before the next `await`.
