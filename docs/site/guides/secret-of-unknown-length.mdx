This is your situation when you build something secret piece by piece and cannot know its size before you start,
such as a key serialized as JSON, and the result must then go to an API that takes one span, such as an encryption
call. The example serializes a key document and encrypts it for storage.

You'll use `BufferFactory.CreatePooledBufferWriter` · `Utf8JsonWriter` · `ConsumeAsContiguousSpan` ·
`GetSpanLease` · `AesGcm`

## The usual code

A growable writer under a `Utf8JsonWriter`, then one array for the encryption call.

<Pinned tone="usual">
```cs snippet=SiteUnknownLengthUsual title="KeyStore.cs" "new ArrayBufferWriter<byte>()" "WriteBase64String(" "ToArray()"
```
</Pinned>

**Leaves behind**

<PinNotes tone="usual">

1. A copy of the document so far, each time the writer grows: it allocates a larger array, copies into it, and
   drops the smaller one with the first part still in it. <LeakCard leak="L4" />
2. The key, as base64 text, in the writer's last array: ordinary heap memory that the collector can move, and that
   nothing clears. <LeakCard leak="L1" /> <LeakCard leak="L2" />
3. One more copy of the whole document, made by `ToArray()`. <LeakCard leak="L9" />

</PinNotes>

The first leak is invisible in the code. This test keeps a view of the writer's array, writes past its end, and
finds the first 16 bytes still in the array it dropped:


## With NCode.Buffers

The same job. `CreatePooledBufferWriter` returns Nerdbank.Streams' `Sequence<byte>`, an `IBufferWriter<byte>` that
rents its segments from the library's pool of pinned buffers. <Proof source="BufferFactory.CreatePooledBufferWriter" />

<Pinned tone="fix">
```cs snippet=SiteUnknownLengthWriter title="KeyStore.cs" "CreatePooledBufferWriter(isSensitive: true)" "WriteBase64String(" "ConsumeAsContiguousSpan("
```
</Pinned>

**What changed**

<PinNotes tone="fix">

1. The writer grows by adding a segment. Nothing already written is copied or dropped, and every segment is pinned:
   a 4096-byte page from the pool, or a pinned array of its own for a request larger than that.
   <Proof sample="SiteGrowthLeavesCopies" /> <Proof sample="SiteSegmentsArePinned" />
2. The key's base64 text is written into those segments, and disposing the writer overwrites them with zeros.
   <Proof claim="R1" />
3. The document reaches `Encrypt` as one span, without `ToArray()`. In one segment, the span is the writer's own
   memory; across several, it is a copy in one sensitive buffer, zeroed when you dispose `owner`.
   <Proof sample="SiteLeaseOrConsume" />

</PinNotes>

The writer's first segment is one page from the pool.
<Proof test="BufferFactoryTests.CreatePooledBufferWriter_WhenSensitive_RentsWholePagesFromSecurePool" /> The test
runs the method with a document of one segment and with one of two, and checks that both decrypt to the same bytes as
the usual code's. <Proof sample="SiteUnknownLengthWriter" />

## Read it as one span

Pick by what the code that reads the secret needs.

1. **It takes pieces**, as a hash or a MAC does. Feed it one segment at a time, and nothing is copied.

   ```cs snippet=SiteContiguousIncremental title="Authenticate the document where it is"
   ```

2. **It needs one span, and you still need the writer.** Take a lease, and dispose it before the writer.

   ```cs snippet=SiteUnknownLengthLease title="Lease the document, keep the writer"
   ```

3. **It needs one span, and you are done with the writer.** Consume it, as the example above does.

The two calls differ only when the writer holds more than one segment:

| | One segment | Several segments |
| --- | --- | --- |
| `GetSpanLease` | A span over the writer's own memory. No copy, and no owner: disposing the lease leaves the writer as it was | A copy, rented with the `isSensitive` you pass. Disposing the lease releases the copy; the writer keeps its data |
| `ConsumeAsContiguousSpan` | The writer's own memory. The owner it returns is the writer itself | A copy. The call disposes the writer before it returns, and the owner it returns is the copy's |

<Proof test="SequenceExtensionsTests.GetSpanLease_SingleSegment_Dispose_DoesNotResetSequence" />

<Proof test="SequenceExtensionsTests.ConsumeAsContiguousSpan_MultipleSegments_DisposesOriginalSequence" />

While a lease over several segments is open, the secret is in two places. Where one segment ends is Nerdbank.Streams'
choice, so write code that handles both columns, as the three ways above do.

## Pitfalls

Each is also in [Ways to get it wrong](/reference/pitfalls/), with its evidence.

- **No `using` on the writer.** *You write* `var writer = …`. *What happens:* nothing is zeroed, because nothing
  calls `Dispose` for you. *Write instead:* `using var writer`.
  [No using statement](/reference/pitfalls/#no-using-statement)
- **A lease or a copy that is not sensitive.** *You write* `GetSpanLease(isSensitive: false)` on a sensitive writer.
  *What happens:* a document of several segments is copied into a shared-pool buffer, neither pinned nor zeroed. <Proof source="SequenceExtensions.GetSpanLease.Rent" /> *Write instead:* the writer's
  own `isSensitive`. [A lease or a copy with isSensitive false](/reference/pitfalls/#a-lease-or-a-copy-with-issensitive-false)
- **The secret as a string.** *You write* `json.WriteString("k", Convert.ToBase64String(key))`. *What happens:* a
  string of the key exists before the writer sees it. <LeakCard leak="L5" /> *Write instead:*
  `json.WriteBase64String("k", key)`, which takes the bytes. [A string of the secret](/reference/pitfalls/#a-string-of-the-secret)
- **`ToArray()`.** *You write* it on the sequence or on a lease. *What happens:* an ordinary array holds the
  document. <LeakCard leak="L9" /> *Write instead:* a lease, or the segments.
  [A copy you make](/reference/pitfalls/#a-copy-you-make)
- **Changing the writer under a lease.** *You write* a `Dispose` or `Reset` of the writer while a lease is open.
  *What happens:* with one segment the lease's span is the writer's memory, which the writer releases.
  <Proof source="SequenceExtensions.GetSpanLease.Remarks" /> *Write instead:* dispose the lease first, then the writer.
- **Writing again after consuming.** *You write* to the writer after `ConsumeAsContiguousSpan`. *What happens:* the
  call has disposed it, or, with one segment, returned it as the owner you will dispose. <Proof sample="SiteLeaseOrConsume" /> *Write instead:*
  a new writer.

## What this does not fix

:::caution[Outside this guide]
- **The inputs.** The key you serialize must already be in a sensitive buffer.
  [Keep a secret across an await, or in a field](/guides/secrets-across-await/) shows one way to hold it.
- **What the JSON writer does inside itself.**
- **The copy an API makes of the span you give it.** That memory belongs to the API, and so does clearing it.
:::

## Checklist

- [ ] A secret of unknown length is written into `CreatePooledBufferWriter(isSensitive: true)`, in a `using`.
- [ ] No `MemoryStream`, `ArrayBufferWriter<T>`, `List<byte>` or `StringBuilder` holds it.
- [ ] Secret values enter the JSON writer as bytes, never as a `string`.
- [ ] An API that can take pieces is fed the segments.
- [ ] A lease or a consumed owner is taken with `isSensitive: true`, and disposed with `using`.
- [ ] Nothing calls `ToArray()` on the writer, its sequence or a lease.
