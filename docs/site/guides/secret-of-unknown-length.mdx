This is your situation when you build a secret piece by piece without knowing its size, such as a key serialized
as JSON, and then hand it to an API that takes one span. The example serializes a key document and encrypts it for
storage.

## The usual code

A growable writer under a `Utf8JsonWriter`, then one array for the encryption call.

<Pinned tone="usual">
```cs snippet=SiteUnknownLengthUsual title="KeyStore.cs" "new ArrayBufferWriter<byte>()" "WriteBase64String(" "ToArray()"
```
</Pinned>

**Leaves behind**

<PinNotes tone="usual">

1. A copy of the document so far, each time the writer grows: it copies into a larger array and drops the smaller
   one with the first part still in it. <LeakCard leak="L4" />
2. The key, as base64 text, in the writer's last array, which the collector can move and nothing clears.
   <LeakCard leak="L1" /> <LeakCard leak="L2" />
3. One more copy of the whole document, made by `ToArray()`. <LeakCard leak="L9" />

</PinNotes>

The first leak does not show in the code. This test keeps a view of the writer's array, writes past its end, and
finds the first 16 bytes still in the dropped array:

## With NCode.Buffers

The same job, with `CreatePooledBufferWriter`: Nerdbank.Streams' `Sequence<byte>`, which rents its segments from
the library's pool of pinned buffers. <Proof source="BufferFactory.CreatePooledBufferWriter" />

<Pinned tone="fix">
```cs snippet=SiteUnknownLengthWriter title="KeyStore.cs" "CreatePooledBufferWriter(isSensitive: true)" "WriteBase64String(" "ConsumeAsContiguousSpan("
```
</Pinned>

**What changed**

<PinNotes tone="fix">

1. The writer grows by adding a segment, and copies or drops nothing. Every segment is pinned: a 4096-byte page
   from the pool, or a pinned array of its own for a larger request.
   <Proof test="BufferFactoryTests.CreatePooledBufferWriter_WhenSensitive_RentsWholePagesFromSecurePool" />
   <Proof sample="SiteSegmentsArePinned" />
2. The key's base64 text is written into those segments, and disposing the writer overwrites them with zeros.
   <Proof claim="R1" />
3. The document reaches `Encrypt` as one span, without `ToArray()`: the writer's own memory when it is one segment,
   otherwise a copy in one sensitive buffer, zeroed when you dispose `owner`. <Proof sample="SiteLeaseOrConsume" />

</PinNotes>

A document of one segment and one of several both decrypt to the usual code's bytes. <Proof sample="SiteUnknownLengthWriter" />

## Read it as one span

Pick by what the code that reads the secret needs.

**It takes pieces**, as a hash or a MAC does. Feed it the segments; nothing is copied.

```cs snippet=SiteContiguousIncremental title="Authenticate the document where it is"
```

**It needs one span, and you still need the writer.** Take a lease, and dispose it before the writer.

```cs snippet=SiteUnknownLengthLease title="Lease the document, keep the writer"
```

**It needs one span, and you are done with the writer.** Consume it, as the example does.

The two calls differ only when the writer holds more than one segment:

| | One segment | Several segments |
| --- | --- | --- |
| `GetSpanLease` | The writer's own memory, with no owner: disposing the lease leaves the writer as it was | A copy, rented with the `isSensitive` you pass, released with the lease; the writer keeps its data |
| `ConsumeAsContiguousSpan` | The writer's own memory, and the writer is the owner it returns | A copy, whose owner it returns; the call disposes the writer first |

<Proof test="SequenceExtensionsTests.GetSpanLease_SingleSegment_Dispose_DoesNotResetSequence" /> <Proof test="SequenceExtensionsTests.GetSpanLease_MultipleSegments_CopiesDataToContiguousBuffer" /> <Proof test="SequenceExtensionsTests.ConsumeAsContiguousSpan_SingleSegment_ReturnsSequenceAsOwner" /> <Proof test="SequenceExtensionsTests.ConsumeAsContiguousSpan_MultipleSegments_DisposesOriginalSequence" /> <Proof sample="SiteLeaseOrConsume" />

While a lease over several segments is open, the secret is in two places. Where a segment ends is Nerdbank.Streams'
choice, so handle both columns.

## Pitfalls

[Ways to get it wrong](/reference/pitfalls/) has more, each with its evidence.

- **No `using` on the writer.** *You write* `var writer = …`. *What happens:* nothing calls
  `Dispose`, so nothing is zeroed. *Write instead:* `using var writer`.
  [No using statement](/reference/pitfalls/#no-using-statement)
- **A lease or a copy that is not sensitive.** *You write* `GetSpanLease(isSensitive: false)` on a sensitive writer.
  *What happens:* a document of several segments is copied into a shared-pool buffer, neither pinned nor zeroed.
  <Proof source="SequenceExtensions.GetSpanLease.Rent" /> *Write instead:* the writer's own `isSensitive`. [A lease or a copy with isSensitive false](/reference/pitfalls/#a-lease-or-a-copy-with-issensitive-false)
- **The secret as a string.** *You write* `json.WriteString("k", Convert.ToBase64String(key))`. *What happens:* a
  string of the key exists first. <LeakCard leak="L5" /> *Write instead:*
  `json.WriteBase64String("k", key)`, which takes the bytes. [A string of the secret](/reference/pitfalls/#a-string-of-the-secret)
- **`ToArray()`.** *You write* it on the sequence or on a lease. *What happens:* an ordinary array holds the
  document. <LeakCard leak="L9" /> *Write instead:* a lease, or the segments.
  [A copy you make](/reference/pitfalls/#a-copy-you-make)
- **Changing the writer under a lease.** *You write* `Dispose` or `Reset` on the writer while a lease is open.
  *What happens:* with one segment, the lease's span is memory the writer releases.
  <Proof source="SequenceExtensions.GetSpanLease.Remarks" /> *Write instead:* dispose the lease first.

## What this does not fix

:::caution[Outside this guide]
- **The inputs.** The key you serialize must already be in a sensitive buffer, as
  [Keep a secret across an await, or in a field](/guides/secrets-across-await/) holds one.
- **What the JSON writer does inside itself.**
- **A copy the API makes of your span.** Clearing it is the API's job.
:::

## Checklist

- The secret is written into `CreatePooledBufferWriter(isSensitive: true)`, in a `using`.
- No `MemoryStream`, `ArrayBufferWriter<T>`, `List<byte>` or `StringBuilder` holds it.
- Secret values enter the JSON writer as bytes, never as a `string`.
- An API that takes pieces is fed the segments.
- A lease or a consumed owner is sensitive, and in a `using`.
- No `ToArray()` on the writer, its sequence or a lease.
