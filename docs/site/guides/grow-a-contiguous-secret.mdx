This is your situation when you build a secret whose size you do not know up front, and the code that uses it needs
the whole secret as one span: a JSON document you hash, a payload you encrypt, a connection string you assemble. The
examples serialize a key document and hash it, round-trip an object through a stream, and build a connection string
from a password.

You'll use `BufferFactory.CreateContiguousBufferWriter` · `ContiguousBufferWriter<T>` · `BufferFactory.CreatePooledStream`
· `PooledMemoryStream` · `PooledTextBuilder`

## The usual code

It writes into an `ArrayBufferWriter<byte>`, which holds its bytes in one array. When a write does not fit, the writer
allocates a larger array, copies the bytes into it, and drops the old one. Nothing zeroes the old one.

**Leaves behind**

<PinNotes tone="usual">

1. `before` is the array the writer held before the second write. The secret is still in it after the writer moves on,
   until the garbage collector reuses the memory. <Proof sample="SiteGrowUsual" />
2. Each further growth leaves one more array behind, and each one holds the part of the secret written so far.

</PinNotes>

## With NCode.Buffers

`BufferFactory.CreateContiguousBufferWriter` returns a `ContiguousBufferWriter<T>`. It is a pooled `IBufferWriter<T>`
whose data is always one span, `WrittenSpan` or `WrittenMemory`, so a hash or a cipher takes it without a copy. It
rents its buffer when you first write, and it grows by renting a larger buffer, copying the written part into it and
disposing the old owner, which zeroes it when the writer is sensitive. <Proof source="Api.ContiguousBufferWriter" /> <Proof source="Adr1028" />

<Pinned tone="fix">
```cs snippet=SiteGrowContiguousWriter title="Mac.cs" "BufferFactory.CreateContiguousBufferWriter("
```
</Pinned>

**What changed**

<PinNotes tone="fix">

1. `Utf8JsonWriter` writes into the writer, and the writer grows as it needs to. Each buffer it outgrows is zeroed
   before it goes back to the pool. <Proof test="ContiguousBufferWriterTests.Grow_WhenSensitive_ZeroesTheOutgrownBuffer" />
2. `WrittenSpan` is the whole document as one span, so `HMACSHA256.HashData` reads it with no copy.
   <Proof sample="SiteGrowContiguousWriter" />
3. `using` disposes the writer when the scope ends, and the buffer it holds is zeroed then.
   <Proof test="ContiguousBufferWriterTests.Dispose_WhenSensitive_ZeroesTheBuffer" />

</PinNotes>

`Reset()` zeroes the written part and keeps the buffer, so you can reuse the writer for the next secret. A span from
`GetSpan`, `GetMemory` or `WrittenSpan` is not valid after the next call to `GetSpan` or `GetMemory`, because that
call can move the data to a larger buffer. Take `WrittenSpan` again when you need it.

### Through a stream

When the code that writes wants a `Stream`, `BufferFactory.CreatePooledStream` returns a `PooledMemoryStream`. It is a
seekable read-write stream over one pooled buffer. It zeroes each buffer it outgrows, and the bytes that `SetLength`
cuts off. <Proof source="Api.PooledMemoryStream" />

```cs snippet=SiteGrowPooledStream title="RoundTrip.cs" "BufferFactory.CreatePooledStream("
```

`Read`, `Write`, `ReadByte`, `WriteByte`, `CopyTo`, `CopyToAsync` and the async methods copy through no shared array.
The base `Stream` versions of `Read`, `Write` and `CopyTo` copy through arrays rented from `ArrayPool<byte>.Shared`,
and `ReadByte` and `WriteByte` through a new one-byte array; nothing zeroes either, so a stream that does not override
them leaves the secret there. The async members complete synchronously. <Proof test="PooledMemoryStreamTests.Write_PastCapacity_ZeroesTheOutgrownBuffer" /> <Proof test="PooledMemoryStreamTests.Dispose_WhenSensitive_ZeroesTheBuffer" />

<Proof sample="SiteGrowPooledStream" /> [Give pipes and stream readers a pool that cleans up](/guides/pipes-and-streams/)
covers the other stream cases.

### Text

For text, `PooledTextBuilder` appends characters the way a `StringBuilder` does, with its text in one pooled buffer.
It can start in a `stackalloc` span, so short text never rents anything. When the text outgrows the span, the builder
rents a pooled buffer and, when it is sensitive, zeroes your span first. <Proof source="Api.PooledTextBuilder" />

```cs snippet=SiteGrowTextBuilder title="ConnectionString.cs" "new PooledTextBuilder("
```

`PooledTextBuilder` is a `ref struct`, so there are limits:

- It cannot cross an `await`, and it cannot be a field of a class.
- It must never be copied. Pass it to another method by `ref`.
- Its `WrittenSpan` is the text so far, as one span of characters.

## Pitfalls

[Ways to get it wrong](/reference/pitfalls/) has more, each with its evidence.

- **Passing `isSensitive: false` for a secret.** *You write* `CreateContiguousBufferWriter(isSensitive: false)`.
  *What happens:* each buffer it outgrows goes back to the shared pool unzeroed, with the
  secret in it. *Write instead:* pass `isSensitive: true` for every secret. `false` is right for data that is not
  secret.
- **Calling `ToString()` on the builder.** *You write* `builder.ToString()` to get the text. *What happens:* it makes a
  `string`, and a `string` cannot be zeroed. *Write instead:* pass `WrittenSpan` on, or copy it into a
  `Secret<char>`, as the example does.
- **Copying the builder.** *You write* `var other = builder;` or pass it to a method by value. *What happens:* the
  copy and the original each think they own the buffer, and they disagree about its length and who disposes it.
  *Write instead:* pass it by `ref`, and dispose only the original.
- **Letting a secret grow past one page.** *You write* a writer or a stream with the default `initialCapacity`, for a
  secret that reaches many kilobytes. *What happens:* above 4096 bytes (2048 chars), each growth rents a new pinned
  array of its own, which no pool caches, so each growth allocates. *Write instead:* pass an `initialCapacity` near
  the size you expect.
- **Keeping a span across a write.** *You write* `var span = writer.GetSpan()`, then another `GetSpan`, then use the
  first span. *What happens:* the second call can move the data to a larger buffer, and the first span points at the
  old buffer, which is disposed, and zeroed when it is sensitive. *Write instead:* take the span again after each call.

## What this does not fix

:::caution[Outside the growing buffer]
- **A copy you make.** `ToArray()`, `new string(…)` and `ToString()` each make a copy that nothing zeroes.
- **What a library does inside.** A serializer or a hash that takes the span decides for itself what it copies.
  [What it protects, and what it does not](/start/limits/).
- **Unpooled growth.** Above 4096 bytes, each growth rents a pinned array of its own that no pool caches, so each
  growth allocates.
:::

## Checklist

- A secret that grows is written into `CreateContiguousBufferWriter`, `CreatePooledStream` or `PooledTextBuilder`,
  and not into an `ArrayBufferWriter<byte>`, a `MemoryStream` or a `StringBuilder`.
- A secret passes `isSensitive: true`; data that is not secret may pass `false`.
- The writer, stream or builder is disposed with `using`.
- Nothing keeps a span across the next `GetSpan` or `GetMemory`.
- The text builder is passed by `ref` and is never copied, never held in a field, and never kept across an `await`.
- Nothing calls `ToString()` on a builder that holds a secret.
