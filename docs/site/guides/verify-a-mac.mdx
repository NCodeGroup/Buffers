This is your situation when a request carries a value and its MAC, such as a webhook's signature header, a signed
cookie or an API key, and your code must say whether they match. The example verifies a webhook's HMAC-SHA256
signature, sent as hex.

## The usual code

It computes the expected MAC, writes it as hex, and compares the two strings.

<Pinned tone="usual">
```cs snippet=SiteVerifyMacUsual title="Webhooks.cs" "HMACSHA256.HashData(" "Convert.ToHexStringLower(" "== signatureHeader"
```
</Pinned>

**Leaves behind**

<PinNotes tone="usual">

1. The expected MAC, in an array that nothing clears. <LeakCard leak="L2" />
2. The expected MAC again, as a string, which nothing can erase. <LeakCard leak="L5" />
3. A comparison that returns as soon as it finds a difference, so the time it takes depends on how much of the
   signature is right. <LeakCard leak="L7" />

</PinNotes>

The third is the one a sender can use from outside the process: by timing many guesses, it learns how much of each
was right, and builds the expected MAC from the front.

## With NCode.Buffers

The same check. The expected MAC stays on the stack and never becomes text; the header is decoded into bytes and
compared in fixed time.

<Pinned tone="fix">
```cs snippet=SiteVerifyMacWebhook title="Webhooks.cs" "expected.GetSecureLifetime()" "Convert.FromHexString(" "FixedTimeEquals("
```
</Pinned>

**What changed**

<PinNotes tone="fix">

1. The expected MAC is in stack memory the method owns, and `expectedLifetime` overwrites it with zeros at the end of
   the scope, on every way out of it. <Proof claim="R1" />
2. The header is decoded into bytes, so the expected value is never written as text. A header of the wrong length, or
   one that is not hex, returns `false` and throws nothing. <Proof sample="SiteVerifyMacWebhook" />
3. `FixedTimeEquals` reads every byte of two spans of the same length, wherever they differ.
   <Proof claim="R4" />

</PinNotes>

For spans of bytes, the call is .NET's own `CryptographicOperations.FixedTimeEquals`; for any other unmanaged type,
NCode.Buffers' `FixedTimeEquals<T>` views both spans as bytes and calls it. <Proof source="FixedTimeEquals" /> <Proof external="FixedTimeEqualsDocs" />

## If the secret is text

An API key compared as characters takes the same call. With two spans of `char`, it is NCode.Buffers'
`FixedTimeEquals<char>`: an ordinal comparison of UTF-16 code units, so case counts.

```cs snippet=SiteVerifyMacTextSecret title="ApiKeys.cs"
```

<Proof sample="SiteVerifyMacTextSecret" /> Written this way, as a member of `CryptographicOperations`, it is a C# 14
extension member and needs `using NCode.Buffers;`. A project on an earlier language version calls the same method as
`CryptographicOperationsExtensions.FixedTimeEquals`. <Proof source="FixedTimeEquals" />

A key read from configuration is already a `string`; [Read a secret without leaving a string
behind](/guides/read-a-secret-without-a-string/) reads one into a buffer instead.

## Pitfalls

[Ways to get it wrong](/reference/pitfalls/) has more, each with its evidence.

- **Encoding the expected value.** *You write* `Convert.ToHexString(expected)`, and compare strings. *What
  happens:* a string of the expected MAC exists, which nothing can erase. <LeakCard leak="L5" /> *Write instead:*
  decode the value you received, and compare bytes. [A string of the secret](/reference/pitfalls/#a-string-of-the-secret)
- **Decoding before you check the length.** *You write* the length check after decoding, or none. *What happens:* a
  value of the wrong length fills part of the buffer, or does not fit. *Write instead:* check the length first, so it
  is a plain `false`, as the sample does. <Proof sample="SiteVerifyMacWebhook" />
- **Expecting the length to stay hidden.** *You write* a comparison of values whose length is a secret. *What
  happens:* spans of different lengths return `false` at once.
  <Proof test="CryptographicOperationsExtensionsTests.FixedTimeEquals_DifferentLengths_ReturnsFalse" /> *Write
  instead:* compare values of one fixed length, such as the MACs of the two.
- **Comparing values that have more than one encoding.** *You write* `FixedTimeEquals<T>` on `double` values or a
  struct with padding. *What happens:* it compares bytes, not values, so equal values can compare unequal.
  <Proof sample="SitePitfallCompareBytesNotValues" /> <Proof sample="SitePitfallPaddingBytesCount" /> *Write
  instead:* spans of bytes, characters or integers.
  [FixedTimeEquals on values that are not bytes](/reference/pitfalls/#fixedtimeequals-on-values-that-are-not-bytes)
- **Comparing a digital signature by hand.** *You write* code that signs the data again and compares signatures.
  *What happens:* an ECDSA signature differs each time, so there is no expected value. *Write instead:* the
  algorithm's `VerifyData`, which answers `true` or `false`. <Proof sample="SiteVerifySignature" />
  <Proof external="EcdsaVerifyDataDocs" />
- **Leaving the MAC key in an ordinary array.** *You write* the MAC key into a long-lived `byte[]`. *What happens:*
  nothing clears it. <LeakCard leak="L2" /> *Write instead:* a rented sensitive buffer, as [Keep a secret across an
  await, or in a field](/guides/secrets-across-await/) holds one.

## What this does not fix

:::caution[Outside this check]
- **Timing elsewhere in the request,** such as looking up the secret, parsing the body and logging.
- **The length of what you compare.** It shows, as the pitfall above says.
- **Who can read the secret where it is configured,** or the process while the check runs:
  [what it protects, and what it does not](/start/limits/).
:::

## Checklist

- The comparison is `CryptographicOperations.FixedTimeEquals`, never `==`, `Equals`, `SequenceEqual` or
  `StartsWith`.
- The incoming value is decoded to bytes; the expected value is never encoded as text.
- The expected value is under `GetSecureLifetime()`, or another owner that zeroes it.
- A value of the wrong length is rejected before it is decoded.
- The MAC key is held in a buffer that is zeroed when its owner is disposed.
