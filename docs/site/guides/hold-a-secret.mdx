This is your situation when a secret has to live for a while: in a field of a class, in a settings object, across an
`await`. A client secret you load at startup and use on every request is the usual case. Any line that prints the
object can print the secret with it: a log line, an exception message, a crash report's dump of the object. The
examples log an object that holds a client secret, compute a MAC with it, compare it, and fill a key into one.

You'll use `Secret.Create` · `Secret<T>` · `Reveal` · `FixedTimeEquals` · `Dispose`

## The usual code

It keeps the secret in a `string`. A `string` prints in full, so the first `ToString()` or interpolation that reaches
it writes the secret out, and a `string` cannot be zeroed.

2. The `string` stays in memory until the garbage collector reuses it, and nothing zeroes it.

## With NCode.Buffers

`Secret.Create` copies the value into a pinned, pooled buffer that it rents as sensitive. The `Secret<T>` that it
returns is a sealed class, so you can keep it in a field or across an `await`. `ToString()` returns `[REDACTED]`, and
the debugger shows `[REDACTED]` and hides its fields, so logging it or interpolating it does not print the value. <Proof test="SecretTests.ToString_ReturnsRedacted" /> <Proof source="Adr1029" />

### Using it

`Reveal()` returns a `ReadOnlySpan<T>` over the value. It is the one way to read the secret, so a review finds every
read by searching for `Reveal`. <Proof source="Api.SecretT.Reveal" />

```cs snippet=SiteHoldReveal title="Mac.cs" "clientSecret.Reveal()"
```

Use the span for the call that needs it and let it go. `RevealMemory()` returns a `ReadOnlyMemory<T>` for code that
needs memory, and `CopyTo(Span<T>)` copies the value into a span you own, which you must then zero yourself. <Proof sample="SiteHoldReveal" />

### Comparing

`FixedTimeEquals` compares the secret with a span in the same time for any contents of the same length; a span of
another length returns `false` at once.

```cs snippet=SiteHoldCompare title="Check.cs" "stored.FixedTimeEquals("
```

`Equals` compares contents in fixed time too, but it returns `false` at once when the lengths differ, so it reveals
the length. `GetHashCode()` is the length. Do not use a `Secret<T>` as a dictionary key for that reason. <Proof test="SecretTests.Equals_ComparesContents" /> <Proof sample="SiteHoldCompare" />
[Verify a MAC without leaking timing](/guides/verify-a-mac/) covers comparing MACs.

### Writing it in place

When the value does not exist yet, as with a random key, let the action write it straight into the secret's buffer.
`Secret.Create<T, TState>(int length, TState state, SpanAction<T, TState> action)` hands the action a span of the
length you give. If the action throws, the buffer is zeroed and returned, and the exception is rethrown. <Proof source="Api.Secret.Create" />

## Pitfalls

[Ways to get it wrong](/reference/pitfalls/) has more, each with its evidence.

- **Copying the value out with `Reveal().ToArray()`.** *You write* `var bytes = secret.Reveal().ToArray();`.
  *What happens:* the array is a copy that nothing zeroes, and the secret now lives in two places. *Write instead:*
  pass the span from `Reveal()` to the call that needs it. If you need a copy, `CopyTo` a buffer you zero.
- **Making a string from it.** *You write* `Encoding.UTF8.GetString(secret.Reveal())`. *What happens:* the `string`
  prints in full and cannot be zeroed, so it is the problem you started with. *Write instead:* keep the value as bytes
  or characters, and read it with a span.
- **Forgetting `Dispose`.** *You write* `var secret = Secret.Create(value);` with no `using`. *What happens:* the
  buffer is zeroed only when something disposes the secret, so the value stays in memory. *Write instead:*
  `using Secret<byte> secret = …`, or dispose the field in the `Dispose` of the class that owns it.
- **Using it from two threads while one disposes.** *You write* one thread that calls `Reveal()` while another calls
  `Dispose()`. *What happens:* a `Secret<T>` is not thread-safe against `Dispose`; the reader can see zeroes or throw
  `ObjectDisposedException`. *Write instead:* dispose it only when no other thread reads it.
- **Using it after `Dispose`.** *You write* `secret.Reveal()` after `secret.Dispose()`. *What happens:* it throws
  `ObjectDisposedException`, as do `RevealMemory`, `CopyTo`, `FixedTimeEquals` and `Equals` given another secret or
  itself; `Length`, `ToString()`, `GetHashCode()` and `Equals(null)` still answer, without reading the value.
  *Write instead:* keep the secret alive as long as anything reads it.

## What this does not fix

:::caution[Outside the Secret]
- **Storage and encryption.** A `Secret<T>` lives in memory only. It has no serialization, no persistence and no
  encryption, and the library neither locks nor encrypts memory. <Proof source="Adr1018" />
  [What it protects, and what it does not](/start/limits/).
- **A copy you make.** `ToArray()`, `new string(…)` and `ToString()` on the revealed value each make a copy that
  nothing zeroes.
- **The length.** `Equals` and `GetHashCode()` reveal the length of the secret.
- **`SecureString`.** It is not the answer: Microsoft recommends against it for new code.
  <Proof external="SecureStringNotForNewCode" />
:::

## Checklist

- A secret that lives in a field or crosses an `await` is a `Secret<T>`, and not a `string` or a `byte[]`.
- Every read goes through `Reveal()`, so a search for `Reveal` finds them all.
- Nothing copies the revealed value to an array or a `string`.
- Comparisons use `FixedTimeEquals`, and nobody uses `Equals` or `GetHashCode()` on a secret where the length matters.
- A key that does not exist yet is created with `Secret.Create<T, TState>`, so it is written straight into the secret.
- The secret is disposed, and no thread disposes it while another reads it.
