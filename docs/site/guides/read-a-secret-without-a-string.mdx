This is your situation when a secret reaches your code inside text: a field of a JSON body, a base64 or hex value, or
UTF-8 bytes that an API wants as characters. The example reads `client_secret` from a token request and checks it
against the hash you stored.

You'll use `Utf8JsonReader` · `BufferFactory.Rent` · `Convert.TryFromBase64Chars` · `SecureEncoding.UTF8`

## The usual code

Deserialize the body into a record, then turn the secret into bytes to hash it.

<Pinned tone="usual">
```cs snippet=SiteReadSecretUsualJson title="Clients.cs" "string ClientSecret" "Encoding.UTF8.GetBytes("
```
</Pinned>

**Leaves behind**

<PinNotes tone="usual">

1. The secret as a `string`, which nothing can overwrite. The request object keeps it reachable for as long as
   anything holds the object. <LeakCard leak="L5" />
2. The secret again, in an ordinary array that nothing clears. <LeakCard leak="L2" />

</PinNotes>

## With NCode.Buffers

The same check. A `Utf8JsonReader` walks the body's bytes, finds the property by its UTF-8 name, and copies the value
into a rented sensitive buffer.

<Pinned tone="fix">
```cs snippet=SiteReadSecretJson title="Clients.cs" "ValueTextEquals(" "CopyString("
```
</Pinned>

**What changed**

<PinNotes tone="fix">

1. The property is matched by its UTF-8 name in the body's own bytes, so no request object and no `string` of the
   secret is made. <Proof sample="SiteReadSecretJson" />
2. `CopyString` unescapes the value straight into a buffer from `Rent` with `isSensitive: true`, which is pinned, and
   which disposing `owner` overwrites with zeros. <Proof claim="R3" /> <Proof claim="R1" />

</PinNotes>

A JSON value's escaped length is an upper bound for its unescaped length, so the buffer is rented at `ValueSpan.Length`
and sliced to the count `CopyString` returns. The sample's test reads an escaped value, and rejects a `client_secret`
nested deeper or one that is not a string.
<Proof sample="SiteReadSecretJson" />

## When it arrives another way

### As base64 or hex

Decode the text into a rented buffer, sized for the most it can decode to, and slice it to what was written.

```cs snippet=SiteReadSecretBase64 title="A base64 header value"
```

The other decoders take a span the same way, and say how much they wrote: `Base64Url.TryDecodeFromChars` for
base64url, `Base64.DecodeFromUtf8` for base64 that is still UTF-8 bytes, and `Convert.FromHexString` with a `Span<byte>`
destination for hex. <Proof sample="SiteReadSecretBase64" /> The overloads that take a `string` and return `byte[]`,
such as `Convert.FromBase64String`, put the secret in an array of their own.

### When an API needs characters

Some APIs take a password as characters, such as `ImportFromEncryptedPem`. When it arrives as UTF-8 bytes, decode it
with `SecureEncoding.UTF8` into a `char` buffer from `Rent`.

```cs snippet=SiteReadSecretChars title="Keys.cs"
```

`GetCharCount` gives the exact length, and throws `DecoderFallbackException` for bytes that are not UTF-8 before
anything is copied. <Proof sample="SiteReadSecretChars" /> <Proof claim="R5" /> `Rent` works for any unmanaged
element type; one pooled buffer holds 2048 characters. <Proof test="SecureMemoryPoolTests.Rent_CharPool_ReturnsOnePageOfBytes" />
A `string` decoded with `SecureEncoding` can't be zeroed either, so decode into a buffer, as here. <Proof source="Readme.DecodeIntoABuffer" />

## Strings you cannot avoid

Configuration values, environment variables, header values and model-bound properties are strings before your code
runs, and nothing can erase them. <LeakCard leak="L5" /> Convert such a value once, at the edge, into a sensitive
buffer, as the base64 example does. Then pass the buffer, and never log, concatenate or split the string.

## Pitfalls

[Ways to get it wrong](/reference/pitfalls/) has more, each with its evidence.

- **A string by another name.** *You write* `reader.GetString()`, `Encoding.UTF8.GetString`,
  `Convert.ToBase64String`, `Convert.ToHexString` or an interpolated string. *What happens:* each makes a `string`
  of the secret. <LeakCard leak="L5" /> *Write instead:* `CopyString`, `GetChars` into a span, or a decoder that
  writes into one. [A string of the secret](/reference/pitfalls/#a-string-of-the-secret)
- **Using all of an upper bound.** *You write* code that uses the whole buffer you sized with `GetMaxCharCount`, or
  with a JSON value's escaped length. *What happens:* the count is often smaller, and the rest of the buffer was
  never written: for UTF-8, `GetMaxCharCount(n)` is `n + 1`. <Proof sample="SiteReadSecretChars" /> *Write
  instead:* slice to the count the call returns.
  [Reading a new buffer before writing it](/reference/pitfalls/#reading-a-new-buffer-before-writing-it)
- **Forgetting the input.** *You write* code that copies the secret out of the request body and stops there.
  *What happens:* the body still holds it, as the picture shows. *Write instead:* keep the body in memory you can
  clear, and clear it.
- **Logging the decoding error.** *You write* a `catch` that logs a `DecoderFallbackException`. *What happens:* its
  message and `BytesUnknown` carry the rejected bytes, part of the secret.
  <Proof sample="SiteReadSecretChars" /> *Write instead:* catch it at the boundary, reject the input, and log that
  it was rejected, not the exception.

## What this does not fix

:::caution[Outside this guide]
- **The transport's own buffers,** where the request was before your code saw it.
- **A string someone made before your code ran,** such as a configuration value or a model-bound property.
- **The copy an API keeps.** The `ECDsa` object holds the private key it imported; dispose it when you are done.
:::

## Checklist

- No `GetString`, `ReadAllText` or deserialized `string` property holds a secret.
- Values are copied or decoded straight into a buffer from `Rent(…, isSensitive: true, …)`.
- Each buffer is sized with an upper bound and sliced to the count written.
- `DecoderFallbackException` is caught at the boundary, and never logged.
- Every owner is in a `using`.
