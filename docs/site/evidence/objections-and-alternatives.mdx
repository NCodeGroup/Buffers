## In short

- **Each heading is an objection.** It is worded as a reviewer would word it.
- **Each answer starts with where the objection is right.** The answer that follows rests on a test, a compiled
  sample, a source line or a page outside this repository.
- **The table at the end sets the alternatives side by side.** Read it to choose, not to be sold.

## "An attacker who can read memory has already won"

Right for a live process. A secret in use is readable, and whatever can read your process's memory reads it while it is
there. The library does not stop that, and [What it protects, and what it does not](/start/limits/) says so.

What the library changes is how long a secret lasts and in how many places. A buffer is zeroed when you dispose it, so
a dump taken later, a page written to disk later or the next renter of a pooled buffer finds zeros where the key was.
<Proof claim="R1" />

## "The JIT doesn't remove `Array.Clear`"

Right today, as far as anyone shows. No test here makes the runtime drop a clear, and the library does not claim that
one does.

The library does not depend on that staying true. Microsoft keeps `CryptographicOperations.ZeroMemory` for the case:
"This method exists to future-proof against potential optimizations in the .NET runtime that could eliminate memory
writes that aren't followed by memory reads". <Proof external="ZeroMemoryRemarks" /> The owners' `Dispose`, the fixed
writers' `Reset()`, `ZeroMemory<T>` and `FixedTimeEquals<T>` call the methods Microsoft documents for this, and no loop
of the library's own. <Proof source="Adr1016" /> A `Reset()` over elements that hold references sets them to default
with `Span<T>.Clear()`.

Both do what they say, and both keep the discipline in your code: a `try` and a `finally` at every site that holds a
key. The library adds three things. A pool, so a buffer that is rented often is not allocated each time. A `using`,
which zeroes on every way out of a block without a `finally` you write. And the build-time bans, which make the leaky
alternatives fail to compile in your project: [Ban the leaky APIs](/guides/ban-leaky-apis/).

## "Why not `SecureString`?"

Right that its name promises it. Microsoft recommends against it for new code: "We recommend that you don't use the
SecureString class for new development". <Proof external="SecureStringNotForNewCode" /> It does not encrypt its storage
outside Windows. <Proof external="SecureStringNoEncryption" /> Its memory is not pinned, so the collector makes extra
copies of it when it moves memory. <Proof external="SecureStringCopies" />

## "Why not lock or encrypt the memory?"

Right that an attacker who gets a page file or a hibernation file reads a secret that was in memory. The library
does not lock pages, hide memory from a debugger or a dump, or encrypt memory, and it records why: locking is an
operating system call, suspend saves locked pages too, and a key that decrypts memory is one more secret in that
memory. <Proof source="Adr1018" /> [What it protects, and what it does not](/start/limits/) lists it among the limits.

## "What does it cost?"

Something, and this page gives no number. A rented buffer up to a page is zeroed whole on every dispose.
<Proof sample="SiteDisposeZeroesWholePage" /> A larger buffer is a new pinned array each call.
<Proof test="SecureMemoryPoolTests.Rent_LargeBuffer_IsNotPooled" /> The cache has no limit of its own.
<Proof source="Adr1015" /> The library records no metrics <Proof source="Metrics.None" /> and ships no benchmarks:
measure in your workload. [How the buffers work](/concepts/how-the-buffers-work/#what-it-costs) lists each cost with its
evidence.

## "Another dependency"

Right. The package has one: Nerdbank.Streams. JetBrains.Annotations, whose attributes mark the public API for the
IDE, is a build-time reference the package does not list. <Proof source="PackageDependencies" /> <Proof source="Adr1022" />
Nerdbank.Streams is part of the public API, because the pooled buffer writers return its `Sequence<T>`, so every
consumer takes it. The repository records no reason for that choice, and says so. <Proof source="Adr1017" />

## "A `bool` parameter is a smell"

Right in general. Here the `bool` is `isSensitive`, and it has no default: every rental says whether the buffer holds
a secret. <Proof source="PublicApi.IsSensitive" /> A rental that left it out would be a rental that never decided. The
library bans the other buffer and encoding APIs in its own code to keep it that way. <Proof source="Adr1003" />

## "Who maintains it?"

One maintainer, and the page says so. `GOVERNANCE.md` names who does what and how decisions are made.
<Proof source="Governance" /> One person holds owner access to the organization and to the nuget.org package, and the
file says that continuity needs a second owner of both. What it does give is that everything is in the organization,
with no knowledge held elsewhere, and that publishing uses trusted publishing, with no stored key to hand over.
<Proof source="Governance.Continuity" />

## "How do I verify the package?"

[`SECURITY.md`](https://github.com/NCodeGroup/Buffers/blob/main/SECURITY.md) lists the checks to run on a package you
downloaded. <Proof source="VerifyAPackage" /> Every check, with what it proves and what it does not:
[The package](/evidence/package/#verify-the-package).

## "When not to use this library"

Right to ask. Do not use it for data that is not secret and has no fixed size: a plain pool or `ArrayBufferWriter<T>`
does that work without the zeroing, and `isSensitive: false` is there for the buffers that sit beside a secret. Do not
use it for a secret that must stay out of your process: a key store, a hardware security module or an operating system's
credential service holds the key, and your code holds an opaque handle. That is Microsoft's recommendation in place of
`SecureString`. <Proof external="SecureStringOpaqueHandle" />

## Compared

Six ways to hold a secret. A cell says what the approach gives you, not what it can be made to give with enough care.

| Approach | Moved by the collector | Cleared | Pooled | Across `await` | What it needs |
| --- | --- | --- | --- | --- | --- |
| `new byte[]` and `Array.Clear` | Can be: it is not pinned <Proof claim="R3" /> | When your code runs it, on every path | No | Yes | A `try` and a `finally` at every site |
| `ArrayPool<byte>.Shared` with `clearArray: true` | Can be: its arrays are not pinned | When you return the array with `clearArray: true`; otherwise "the array's contents are left unchanged" <Proof external="ArrayPoolReturnDocs" /> | Yes | Yes | `clearArray: true` on every `Return`, and a `Return` on every path |
| `stackalloc` and `ZeroMemory` | No: "isn't subject to garbage collection" <Proof external="StackallocDocs" /> | In your `finally` <Proof sample="SiteAlternativeStackByHand" /> | No | No: a span "can only be stored on the stack" <Proof external="SpanStackOnlyDocs" /> | A small, fixed size, and a `finally` |
| A pinned array by hand | No: it is on the pinned heap <Proof sample="SiteAlternativePinnedArrayByHand" /> | In your `finally` | No | Yes | `GC.AllocateArray` with `pinned: true`, and a `finally` |
| `SecureString` | Its memory is not pinned <Proof external="SecureStringCopies" /> | Not the string you build it from | No | Yes | A recommendation against new use <Proof external="SecureStringNotForNewCode" /> |
| `Rent` with `isSensitive: true` | No: it is on the pinned heap <Proof claim="R3" /> | On `Dispose`, the whole buffer <Proof claim="R1" /> | Yes, up to a page <Proof claim="R2" /> | Yes, as `Memory<byte>` <Proof sample="SiteAcrossAwaitMemory" /> | A `using` around the owner |
