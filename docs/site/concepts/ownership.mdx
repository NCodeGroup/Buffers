## In short

- **The rule.** Every buffer that holds a secret has one owner, an `IDisposable`, and the memory is zeroed in that
  owner's `Dispose` and nowhere else.
- **What you do.** Dispose the owner with `using`, in the tightest scope that still covers the work, or hand the
  owner itself to the code that will dispose it.
- **The limit.** Nothing zeroes an owner you never dispose, and nothing stops a span or an array you kept from being
  read after `Dispose`.

## The problem

A buffer that is zeroed on dispose is only as good as the dispose: the zeroing runs when, and only when, someone calls
it. A span is only as good as the owner behind it: it is a view of memory that belongs to something else, and it
keeps pointing at that memory after the owner is done with it.

.NET draws the same line. Microsoft's guidelines for `Memory<T>` give every buffer one owner, responsible for
destroying it, and consumers that may use it while they hold a lease. Their seventh rule: "If you have an
IMemoryOwner&lt;T&gt; reference, you must at some point dispose of it or transfer its ownership (but not both)".
<Proof external="MemoryOwnershipRule7" /> NCode.Buffers follows that model, and adds that disposing is when the
secret is overwritten. <Proof source="ArchitectureDesignRules" />

## Five owners

What you hold decides what `Dispose` does, what a second call does, and what a span or an array you kept reads
afterwards.

| You hold | `Dispose` | A second `Dispose` | A view kept afterwards |
| --- | --- | --- | --- |
| The `IMemoryOwner<T>` from `BufferFactory.Rent` with `isSensitive: true`, or from a `SecureMemoryPool<T>` | Overwrites the whole buffer with zeros, the part beyond your slice included, then gives it back to its pool | Does nothing | Reaches memory the pool can give to another caller |
| A `SecureArrayLifetime<T>`, from `CreatePinnedArray` | Overwrites the array with zeros. Frees nothing, returns nothing | Zeroes the array again | Is the same array, holding zeros |
| A `SecureSpanLifetime<T>`, from `GetSecureLifetime()` | Overwrites exactly the span it wraps. Releases nothing | Zeroes whatever that memory holds by then | Is the same memory, which still belongs to whoever supplied it |
| The `Sequence<T>` from `CreatePooledBufferWriter` | Gives every segment back to its pool; a sensitive writer's segments are overwritten with zeros first | Runs again without error | Reaches memory the pool can give to another caller |
| A `RefSpanLease<T>`, from `GetSpanLease` | Disposes its owner, when it has one | Disposes the owner again | Depends on the owner |

## When it happens

`using var` disposes at the end of the enclosing block, not after the last line that uses the variable. In a long
method the secret lasts until the method ends. A `using` statement with its own block ends the secret's life where
the work ends:

```cs snippet=SiteOwnershipTightScope title="Scope the owner to the work"
```

<Proof sample="SiteOwnershipTightScope" /> The block disposes on every way out, an exception or an early `return`
included: that is C#'s rule for `using`. <Proof external="UsingStatementDocs" /> A `Dispose()` call you write after
the work does not. <LeakCard leak="L6" />

`BufferFactory.Rent` keeps the same promise inside itself: if it fails after it took a buffer from the pool, it
disposes that buffer before it throws, so a failed call leaves you nothing to dispose.
<Proof source="BufferFactory.Rent.DisposeOnFailure" />

## Order

When a lifetime wraps memory that something else owns, the lifetime must be disposed first: the memory is zeroed,
then it goes back. `using` declarations are disposed in reverse order, so declare the memory's owner first and the
lifetime second. With an array from a pool, zero inside the `try` and return the array in the `finally`:

```cs snippet=SiteOwnershipUsingOrder title="Zero, then give the memory back"
```

The pool in the sample is its own, and the next caller of `Rent` gets the same array with its first 32 bytes zero.
<Proof sample="SiteOwnershipUsingOrder" /> Disposed the other way round, the lifetime would zero memory that already
belongs to someone else, and the bytes would have gone back with your secret in them.

## Handing it over

To give a buffer to a caller, return its owner and let the caller dispose it: the `IMemoryOwner<T>`, or the
`SecureArrayLifetime<T>` itself. Never return the array or a span from inside the scope that disposes it: the caller
gets the memory after it was zeroed.

```cs snippet=SiteOwnershipReturnLifetime title="The caller owns what this returns"
```

The caller holds the key until its own `using` ends, and then it is zeros. <Proof sample="SiteOwnershipReturnLifetime" />
[Returning the array from inside the scope](/reference/pitfalls/#returning-the-array-from-inside-the-scope) shows
the other way, which compiles.

A lifetime is a struct that holds one reference. Copy it, with `var copy = lifetime;` or by passing it by value, and
you have a second owner of the same array: disposing either one zeroes it for both. Pass the span, not the lifetime,
to code that only uses the memory. [Copying a lifetime](/reference/pitfalls/#copying-a-lifetime) has the test.

## Sensitivity travels with the data

`isSensitive` is a decision about memory, and it is made again wherever the data moves into new memory:

- **The writer.** `CreatePooledBufferWriter(isSensitive: true)` rents every segment from the pinned pool. The value
  is fixed when you create the writer. <Proof test="BufferFactoryTests.CreatePooledBufferWriter_WhenSensitive_RentsWholePagesFromSecurePool" />
- **The lease and the consumed span.** When the data is in several segments, `GetSpanLease` and
  `ConsumeAsContiguousSpan` copy it into a buffer they rent with the `isSensitive` you pass them, not the writer's.
  <Proof source="SequenceExtensions.GetSpanLease.Rent" /> With `false`, that copy comes from the shared pool, which
  neither pins nor zeroes it. <Proof test="BufferFactoryTests.ChoosePool_WhenNotSensitive_ReturnsSharedPool" /> Pass
  the writer's own value.
- **The copy you make.** `ToArray()` and its kind return new, ordinary memory. <LeakCard leak="L9" />

`ConsumeAsContiguousSpan` also takes ownership: with several segments it disposes the writer before it returns, and
the owner it returns is the copy's. <Proof source="SequenceExtensions.ConsumeAsContiguousSpan.Dispose" /> Dispose
that owner, and do not use the writer again.

## What it does not do

**There is no guard against use after `Dispose`.** A span or a `Memory<T>` you kept still points at the memory, and

reads zeros. Either way, drop every view of the memory when you dispose its owner.

## Why it is built this way

The library has one design rule for this: whatever rents memory returns an `IDisposable` owner, and the memory is
zeroed and returned only through `Dispose`. <Proof source="ArchitectureDesignRules" /> Three facts follow from it:

- **No finalizer.** An owner you do not dispose is not zeroed later, so the rule has no exception: no `Dispose`, no
  zeroing.
- **No disposed flag on the lifetimes.** A `SecureArrayLifetime<T>` holds one reference and a `SecureSpanLifetime<T>`
  one span, and nothing else. That is why they cost nothing to copy, why a copy is a second owner, and why a second
  `Dispose` zeroes again instead of checking a flag. <Proof source="SecureArrayLifetime.Unmanaged" />
- **Ref structs where they can be.** The compiler keeps a lifetime out of fields, lambdas and `await`, so it cannot
  outlive the method that disposes it; [the compiler errors](/reference/pitfalls/#it-did-not-compile) are listed
  with the rest of the pitfalls. Where the memory must cross an `await` or live in a field, the owner is an
  `IMemoryOwner<T>`, a class that can.
