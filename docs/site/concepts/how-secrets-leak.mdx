## In short

- **The problem.** A .NET process keeps a secret wherever the runtime and your code put it: in arrays the collector
  can copy, in memory it takes back without erasing, in pools, in strings and in copies.
- **What the library changes.** Buffers the collector does not move, overwritten with zeros when you dispose them, a
  writer that grows without copying, a fixed-time comparison and text encodings that reject invalid input.
- **The limit.** Nothing reaches a string or a copy your code makes, and anyone who can read your process while the
  secret is in use can read the secret.

## Two leaks that are not about memory

A secret can also leak through how long a check takes, and through text that is not what its bytes said.

<HowSecretsLeakFrame leak="L7">
<LeakCard leak="L7" variant="full" id="an-early-exit-tells-time" />
</HowSecretsLeakFrame>

**What an early exit gives away.** The position of the first byte that differs, one guess at a time. In the model
above, someone who can measure the difference finds a 4-byte value one position at a time, in at most 256 guesses per
byte, 1,024 in all, where a blind search could need 4,294,967,296. That is arithmetic on a model, not a measurement
of .NET.

**What a fixed-time comparison still gives away.** The length. Spans of different lengths return `false` at once.
<Proof test="CryptographicOperationsExtensionsTests.FixedTimeEquals_DifferentLengths_ReturnsFalse" /> Microsoft
documents the comparison as taking "an amount of time that depends on the length of the sequences, but not their
values". <Proof external="FixedTimeEqualsDocs" />

**Why the library calls .NET.** `CryptographicOperations.FixedTimeEquals<T>` views both spans as bytes and passes
them to .NET's own `FixedTimeEquals`, in chunks of at most `int.MaxValue` bytes. It compares every chunk, whatever an
earlier chunk held, and leaves each byte to .NET, so the timing is .NET's documented behavior and no loop of the
library's own exits early. <Proof source="FixedTimeEquals" /> <Proof test="CryptographicOperationsExtensionsTests.FixedTimeEqualsInChunks_WhenOnlyTheFirstChunkDiffers_ReturnsFalse" />
No test measures the time, as [R4](/evidence/guarantees/#fixed-time) says.

<HowSecretsLeakFrame leak="L8">
<LeakCard leak="L8" variant="full" id="a-lenient-decoder-invents-characters" />
</HowSecretsLeakFrame>

**The bytes you checked are not the string you used.** Code that checks or hashes the bytes of an input, then works
with the decoded text, can be handed two different inputs that become one string. A strict decoder refuses both
before any text exists.

**What strictness does not give you.** Normalization, case folding, and protection from characters that look alike:
two valid strings that read the same are still two different strings. <Proof claim="R5" />

[Reject malformed UTF-8 and ASCII](/guides/strict-decoding/) shows the fix for the second.

## Does it matter?

A secret left in memory matters when something reads that memory after your code is done with the secret:

- a crash dump, written when the process fails later;
- a page of memory the operating system wrote to disk;
- a bug that reads past the end of a buffer;
- the next caller that rents the same pooled array.

It does not stop anyone who can read the process while the secret is in use: a debugger, a crash dump taken at that
moment, or code running with the process's rights. NCode.Buffers shortens how long a secret lasts and in how many
places; [What it protects, and what it does not](/start/limits/) draws that line in full.

## What stays true whatever you use

- A secret in use is readable by anything that can read the process.
- Memory is not locked into RAM: the operating system can still write it to disk.
- Nothing is zeroed without `Dispose`, and there is no finalizer to do it later. <Proof sample="SiteNoFinalizer" />
- A copy your code makes is new memory that nothing zeroes. <Proof sample="SiteCopiesAreNotCleared" />

[What it protects, and what it does not](/start/limits/) has each of these with what addresses it.

## How we know

Every card names its receipts, each marked by its kind. Eleven are tests in the repository, and all of them pass on
every pull request: five are the library's own, and six are samples of this site, which compile against the public
API only. The rest are two lines of the library's source and Microsoft's documentation of the runtime, linked with
the date it was read.

A test cannot watch the collector move an array, because when it compacts is the collector's decision. So no test on
this site asserts that an ordinary array moved: [L1](#the-collector-moves-arrays) rests on Microsoft's description of
compaction, and the tests assert where the library's buffers are allocated, through the generation the collector
reports.

## Why it is built this way

The library does as little as it can itself. It allocates with .NET's pinned allocation, zeroes with
`CryptographicOperations.ZeroMemory`, compares with `CryptographicOperations.FixedTimeEquals`, and makes its strict
encodings from .NET's own UTF-8 and ASCII encodings set to throw. <Proof source="SecureMemory.Allocate" /> <Proof source="ZeroMemory" /> <Proof source="FixedTimeEquals" /> <Proof source="SecureEncoding.UTF8" />

`ZeroMemory` is the zeroing call .NET keeps for this purpose: Microsoft writes that it "exists to future-proof against
potential optimizations in the .NET runtime that could eliminate memory writes that aren't followed by memory reads".
<Proof external="ZeroMemoryRemarks" /> Each line of the library that touches a secret is short enough to read, and
each one stands on behavior .NET documents.

The owners are `IDisposable` so that C#'s `using` runs the zeroing on every way out of a block, an exception
included, and nothing else zeroes: there is no finalizer to rely on. [Ownership](/concepts/ownership/) says who
disposes what, and when.
